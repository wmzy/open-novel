# open-novel 工具使用指南

> open-novel 是 AI 驱动的长篇小说创作系统。
> 技术栈：React 19 + Hono + PGlite + Drizzle + Linaria + Vite + 内置 Pi Agent SDK（BYOK）

---

## 1. 快速开始

### 1.1 启动开发服务器

```bash
pnpm install
pnpm dev          # 启动 vite dev server（含 API），默认端口 3006
```

生产构建：

```bash
pnpm build        # build:client + build:server
pnpm start        # node dist/server/api.js
```

### 1.2 前置条件

- 在「设置 → 内置 Pi 模型」填写 provider、模型与 API Key；或在环境变量中设置
  `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `DEEPSEEK_API_KEY` / `GEMINI_API_KEY` 之一。
- 订阅用户：先在本地启动 OpenAI/Anthropic 兼容反向代理，再把 Base URL 填到设置页。
- run 超时配置：环境变量 `AGENT_TIMEOUT_MS`（默认 1800000 = 30 分钟）

### 1.3 网络暴露与访问控制（可选）

服务默认只监听 `127.0.0.1`（生产 `HOST` 与 Vite dev server 一致），本机之外无法访问。需要局域网 / 容器访问时：

```bash
AUTH_TOKEN="$(openssl rand -hex 24)" HOST=0.0.0.0 npm start
```

- 设置 `AUTH_TOKEN` 后，除 `/api/health` 外的所有 `/api/*`（含 `/api/projects/:id/events`、`/api/runs/:id/events` 等 SSE 流）都需要认证；静态资源保持开放。
- 浏览器一次性登录：打开 `http://<host>:<port>/api/health?token=<AUTH_TOKEN>`。服务校验后写入 HttpOnly Cookie（`open_novel_auth`，30 天，SameSite=Lax），并 302 到剥离了 `token` 的地址；`EventSource` 无法自定义请求头，因此依赖此 Cookie。
- 脚本可直接带 `Authorization: Bearer <AUTH_TOKEN>`。
- 未授权返回 401 `UNAUTHORIZED`；前端收到 401 会弹出登录指引 toast。
- 仅当显式设置 `HOST` 为非回环地址且未设置 `AUTH_TOKEN` 时启动会打印安全警告（不阻止启动）；日志不输出令牌。
- 令牌比对为常量时间（SHA-256 后再 `crypto.timingSafeEqual`）。

### 2.1 创作流程（七阶段）

open-novel 的创作分七个阶段，每个阶段由 agent 通过 API 触发，产出写入 `.novel/` 目录：

```
concept → world → characters → outline → scenes → sample → writing
 构思     世界观    角色档案     大纲      场景表    样章门    正文写作
```

**样章门（sample）**：scenes 与 writing 之间的强制关卡——写 3 章样章（第 1 章 + 自选 2 个关键章节）检验声口与节奏，每章在 `.novel/sample-feedback.md` 追加复盘（声口落地/节奏体感/世界观落地/大纲需修正点），3 章完成后按复盘修订大纲再进入正式写作。后端门禁：`POST /api/runs` 的 `stage` 为 **writing / drafting / revision / polish** 时扫描磁盘 `.novel/chapters/` 与 `.novel/degraded/` 目录，有效正文（CJK 字数 ≥100）不足 3 章返回 409 `sample-gate`（质检归档章节同样计入，归档可一键恢复，不重新卡门；409 响应带 degradedChapters 章号列表），携带 `force: true` 可旁路；存量项目（≥3 章）不受影响。revision/polish 同样拦截——否则「`/revision` 写第2章」即可绕过样章门。**复盘门**：以 config.json `sampleStageCompleted` 标记为判据（sample run 成功后磁盘正文 ≥3 章时自动写入）——经历过样章阶段就要求 sample-feedback.md 中 ≥3 篇结构化复盘（`- **声口落地**：` 节标题计数，旧格式回退子串计数），文件缺失/不足同样返回 409 `sample-gate`（feedbackCount 字段给出实际篇数）；存量项目无标记时回退旧判据（复盘文件存在则要求 ≥3 篇）；`import-source` 逆向拆书项目（config.json `sourceImported: true`）豁免复盘要求。force 旁路会落盘记录（config.json `sampleGateBypassed: true`），总览页黄色警示徽标；门槛后续达标时自动清除（惩罚可逆）。前端收到 409 后显示双按钮：「去写样章」/「仍要开始正式写作」（二次确认后 force 旁路）。

**阶段切换**：顶部进度条点击、或对话面板工具栏的阶段下拉，都会 `PATCH /api/projects/{id}` 落库 `currentStage`（写作子模式 drafting/revision/polish 仅切视图不落库）。切换后立即发送的消息即按新阶段组装提示词，无需等 agent 回写阶段。`POST /api/runs` 的 `stage` 有枚举校验：未知值返回 400 `invalid-stage`（合法值 = 七阶段 + drafting/revision/polish/decompose/enrich）。

**提问挂起上限**：规划阶段的采访式提问（ask）挂起期间 run 超时计时暂停（用户思考不计时），但提问本身有最长挂起时限 `ASK_TIMEOUT_MS`（默认 24 小时）——到期自动结束整个 run（agent 不再带着缺省答案继续写盘），防止用户关闭浏览器后 run 与项目写锁被永久占用；到期前 1 小时经 SSE 推送提醒。提问挂起期间项目其他写操作锁定，前端有提示。提问过期后用户提交的答案会暂存（响应带 `late: true`），经重试端点回传并补入重试请求，不静默丢弃。

**deepen 收敛准则**：深化审查报告的每条发现必须标注 `[P0]`（结构性缺陷）/`[P1]`（重要问题）/`[P2]`（打磨建议）。当某轮审查无 P0/P1 时视为收敛：修订轮改为冻结轮——P2 建议逐条记入 `.novel/deepen-backlog.md`，禁止再修改产出文件。防止"审查永远找得出问题"的规划螺旋。

**滚动式大纲**：大纲章节卡片带三级承诺等级（引用行元数据 `> commitment: committed|tentative|open`，`open` 须附 `> open-questions:` 待决策列表）。粒度梯度近细远粗：第 1-10 章 committed/beat 级，第一幕其余 tentative/arc 级，二三幕 open/骨架级——远期粗粒度是设计而非未完成。写作 prompt 会按当前进度注入"精排窗口"提醒（已写章节向后 10 章应精化为 beat 级）。`outline/index.md` 在每次合并读取时自动重建自愈（章号取自卡片文件名）。

### 阶段产出文件

| 阶段 | 产出文件 | 内容 |
|---|---|---|
| concept | `.novel/concept.md` | 核心概念、前提、主要冲突 |
| world | `.novel/world-building.md` | 世界设定、规则、历史、文化 |
| characters | `.novel/characters/profiles.md` | 角色动机、背景、关系、弧光 |
| outline | `.novel/outline-detailed.md` | 逐章大纲（幕、节拍、字数分配） |
| scenes | `.novel/scenes.md` | 逐章场景（主动 Scene / 被动 Sequel） |
| sample | `.novel/chapters/第N章.md` + `.novel/sample-feedback.md` | 3 章样章 + 复盘（声口/节奏/世界观/大纲修正） |
| writing | `.novel/chapters/第N章.md` | 正文 + `.summary.md` + `state.json` |

### 阶段推进

每阶段完成后，agent 通过内置 `open_novel_api` 工具调用 PATCH 推进阶段：

```bash
curl -X PATCH http://localhost:3006/api/projects/{projectId} \
  -H "Content-Type: application/json" \
  -d '{"currentStage": "world"}'
```

## 3. 核心 API

### 3.1 项目管理

```bash
# 创建项目
POST /api/projects
{
  "title": "令牌",
  "genre": "wuxia",
  "chapterCount": 20,
  "targetWords": 80000
}

# 获取项目信息
GET /api/projects/{id}

# 更新阶段
PATCH /api/projects/{id}
{ "currentStage": "writing" }

# 生成逐章模板脚手架（大纲/场景）
POST /api/projects/{id}/generate-templates

# 预览模板（不落盘）
GET /api/projects/{id}/templates/outline-detailed
GET /api/projects/{id}/templates/scenes
```

### 3.2 触发 Agent 写作（核心）

```bash
POST /api/runs
{
  "projectId": "proj_xxx",
  "agentId": "pi",            # 内置 Pi（旧值 claude/opencode/omp 仅作兼容别名）
  "stage": "writing",          # concept|world|characters|outline|scenes|writing
  "skillId": "wuxia",          # 插件技能 ID（决定写作风格指导）
  "message": "你的指令..."     # 具体任务描述
}
```

**响应**：
```json
{ "runId": "d2e0ed05-...", "conversationId": "conv_xxx" }
```

**事件流**：通过 SSE 实时获取 agent 事件：
```
GET /api/runs/{runId}/events      # SSE 流
```

**`cost_alert` 事件（run 级预算提醒）**：设置了 `cost_budget_usd` 后，服务端在 run 启动时快照项目
累计花费，并在每条 `runtime_usage` 上累加本次 run 成本；首次越过预算时推送一次：

```json
{ "type": "cost_alert", "spentUsd": 1.25, "budgetUsd": 1, "percent": 125, "runCostUsd": 0.3 }
```

启动时已超支也会立即推送（`runCostUsd` 为 0）。该事件只提醒一次/run，前端显示可关闭的横幅；
成本明细与预算编辑见侧栏「成本」视图（`GET /api/projects/{id}/costs/summary|budget`）。

### 3.3 质量检查

```bash
# AI 味检测（检测碎片化句型、重复词等）
POST /api/projects/{projectId}/check/ai-patterns
{ "chapterNum": 18 }

# 伏笔遗忘 / 债务检测（query threshold 可调）
POST /api/projects/{projectId}/check/foreshadows?threshold=5

# 人物 OOC 检测
POST /api/projects/{projectId}/check/ooc
{ "chapterNum": 18 }

# 事实核查（非阻断、只报告）
POST /api/projects/{projectId}/check/fact-check
{ "chapterNum": 18, "agentId": "pi", "deep": true }
```

事实核查分两层：

- **机械检查**（始终运行，秒级）：POV 知情越界启发式（同段落内使用了「尚不知」或尚未到 `learnedIn` 章的信息）+ 名册人名近似笔误（编辑距离 1，含别名）。
- **语义检查**（`deep: true`，默认开启）：调用一次内置 Pi，返回 `pov-leakage`（POV 越界）、`name-inconsistency`（人名/别名不一致）、`canon-contradiction`（设定/时间线矛盾）三类问题，每条带 `severity`、`chapter`、`quote`。`deep: false` 时只跑机械检查。

**POV 知情边界**保存在 `.novel/character-knowledge.json`（与 `state.json` 的 `characters[].knows` 合并使用）：

```json
{
  "characters": [{
    "name": "林青",
    "knows": [{ "fact": "密道在厨房后面", "learnedIn": 2 }],
    "doesNotKnow": ["自己的真实身世"],
    "updatedChapter": 3
  }]
}
```

写作提示词只在视点角色存在知情数据时注入「POV 知情边界」区块（已知事实按 `learnedIn ≤ 当前章` 过滤），无数据时提示词保持不变。某条事实在正文中获知后，应从 `doesNotKnow` 移除并迁入 `knows`（标注 `learnedIn`）。写作 agent 每章定稿后以 state-patcher 视角更新该文件；事实核查面板的「快速检查」不需要 agent，「AI 语义核查」使用当前对话选择的 agent。所有事实核查结果均不阻断写作，也不改变样章门 / CJK≥100 阈值。

### 3.3.1 Canon 台账与章节合同（长篇一致性）

Canon 是 Markdown 设定之外的结构化事实层；章节合同是每章的硬约束。

**文件**

- `.novel/canon/canon.json`：实体、有效事实、角色知情边界
- `.novel/canon/changes.jsonl`：append-only 变更日志
- `.novel/contracts/第N章.json`：POV / 出场 / beat / 必须揭示 / 禁止揭示 / 字数预算
- `.novel/canon/overrides.jsonl`：强制定稿留痕

**追加 canon 变更**

```bash
POST /api/projects/{projectId}/canon/changes
{
  "chapter": 8,
  "changes": {
    "entities": [{ "name": "林岚", "type": "character", "aliases": ["阿岚"] }],
    "facts": [{ "subject": "林岚", "predicate": "location", "object": "后山" }],
    "knowledge": { "林岚": { "knows": ["真凶身份"], "doesNotKnow": ["掌门立场"] } }
  }
}
```

同一 `subject + predicate` 的新事实会自动把旧事实标记为 `superseded`，并写 `validTo`。

**写入章节合同**

```bash
PUT /api/projects/{projectId}/contracts/3
{
  "pov": "林岚",
  "cast": ["林岚", "师父"],
  "beats": ["山门夜谈", "发现密信"],
  "mustReveal": ["密信"],
  "mustNotReveal": ["真凶身份"],
  "wordBudget": { "min": 2500, "max": 4500, "target": 3500 },
  "status": "frozen"
}
```

**确定性校验**

```bash
POST /api/projects/{projectId}/contracts/3/validate
```

返回 `findings`（`blocker` / `major` / `minor`）：

- `blocker`：POV 未出现、禁止揭示内容提前出现
- `major`：合同出场角色缺失、必须揭示内容缺失、字数越界
- `minor`：合同未冻结、合同角色不在 canon 实体表

写作 run 结束时若存在合同，会推送 `contract-check` 与状态行；定稿（`PATCH /chapters/:num {status:"finalized"}`）前会再校验一次，存在 blocker 时返回 409 `contract-gate`。前端会弹出确认框；确认后携带 `force: true` 强制定稿，并写入 `overrides.jsonl`。

写作 prompt 会自动注入当前 canon 摘要与章节合同（存在时），作为硬约束；合同未冻结时只提示，不阻断。

### 3.3 伏笔债务系统

伏笔是结构化数据（`.novel/foreshadow.json`），字段：`type`（chekhov/identity/emotional/world）、`status`（pending/planted/progressing/resolved/dropped）、`plantedIn`/`resolveDeadline`/`resolvedIn`（严格章号）、`progressedIn`（推进记录章号数组）、`dependsOn`（前置伏笔 id 列表）、`weight`（major/light）。旧格式（plantedIn 为自由文本、缺 progressedIn）读取时自动迁移/补默认值。

状态机：`pending → planted → progressing → resolved`，`planted` 也可直接 `resolved`；未结清状态均可 `dropped`。回退迁移（如 `progressing → planted`、`resolved → planted`）返回 400，须在 PATCH body 显式传 `"reopen": true`（只能回到非终态 pending/planted/progressing）。进入 `progressing` 时自动把当前章号（或 body 中的 `chapter`）追加到 `progressedIn`；也可在 PATCH body 显式传 `progressedIn` 数组修正记录（去重升序）。

```bash
# 清单 + 债务统计（debtScore/overdue/dueSoon/orphaned/密度）+ 顶层 overdue/dueSoon/overdueIds
GET /api/projects/{projectId}/foreshadows

# CRUD
POST   /api/projects/{projectId}/foreshadows          # 创建
PATCH  /api/projects/{projectId}/foreshadows/{fid}    # 更新（status 迁移 / progress / reopen）
DELETE /api/projects/{projectId}/foreshadows/{fid}    # 删除（自动清理依赖引用）
```

逾期判定：`status` 非 resolved/dropped 且 `resolveDeadline < 当前写作章号`（等于当前章视为「本章到期」，不算逾期）。写作 prompt 注入密度预算（默认"每 3 章新埋 ≤2 条"）与有界的「逾期/临期」提醒块；前端伏笔视图为五列看板（待埋/已埋/推进中/已收/放弃）+ 债务摘要条 + 逾期徽章 + 甘特图（◆=期限，⚠=逾期/迟到）。

### 3.4 回溯影响分析（设定修订）

```bash
# 修改设定文件后，扫描受影响面（正文提及/大纲提及/伏笔提及），报告落盘 .novel/retro/
POST /api/projects/{projectId}/retro
{ "file": "world/index.md", "note": "修订说明" }

# 状态卫生：检测规划期数据对运行态 state.json 的污染（只读）
GET /api/projects/{projectId}/state-hygiene
```

状态分离约定：`.novel/state.json` 只存运行态（由正文产生）；规划期期望写入 `.novel/state-intent.json`。每次写作 run 结束时自动执行污染分离自愈（`splitPlanningPollution`）。

### 3.4 章节管理

```bash
# 列出所有章节（GET 时自动按磁盘全量 resync：补缺失、刷新字数、删除磁盘已不存在的行）
GET /api/projects/{projectId}/chapters

# 创建章节：DB 行 + 磁盘空正文文件（含标题行）同步创建，文件已存在时不覆盖
POST /api/projects/{projectId}/chapters

# 手动重新同步磁盘章节到 DB（全量对齐：磁盘是事实源，DB 仅缓存元数据）
POST /api/projects/{projectId}/chapters/resync

# 删除章节（同步删除正文与摘要文件，避免 resync 加回；自动清理伏笔 plantedIn/resolvedIn/progressedIn 悬挂引用；
# 支持 ?renumber=true 或 body { renumber: true }：后续章节章号前移一位——正文/摘要/大纲卡片/DB 行/伏笔引用（含 resolveDeadline/progressedIn）同步平移，避免章号空洞导致「写下一章」永远回到被删章号）
DELETE /api/projects/{projectId}/chapters/{num}?renumber=true

# 列出质检归档章节（.novel/degraded/ 隔离目录 + 旧版 chapters/*.degraded.md）
GET /api/projects/{projectId}/chapters/degraded

# 恢复归档章节到正文（目标章节已存在正文时返回 409，避免覆盖重写内容）
POST /api/projects/{projectId}/chapters/degraded/{num}/restore

# 导出（markdown 支持 ?scope=manuscript 仅正文，默认 full 含概念/世界观/角色设定）
GET /api/projects/{projectId}/export/markdown
GET /api/projects/{projectId}/export/text
# EPUB 3（mimetype 首条不压缩 + container/OPF/nav + 每章 XHTML）与 DOCX（标题页 + Heading 1 + 中文首行缩进）
# 均支持 ?scope=full 附带设定资料，默认仅正文；文件名按 RFC 5987 filename* 返回
GET /api/projects/{projectId}/export/epub
GET /api/projects/{projectId}/export/docx
```

写后质检（退化终检/AI 味检测）不通过时：仅成功且写作产出阶段（writing/sample/drafting）的章节会被移入 `.novel/degraded/` 隔离目录——不再就地改名隐藏；写作视图显示「已归档」分组，可一键恢复。失败 run 与 revision/polish/decompose 只告警不归档，避免误伤导入原文与修订稿。

回滚快照（`POST /api/runs/projects/{id}/rollback`）后服务端会自动 resync 章节表，避免写作视图出现幽灵章节。回滚是**完整回滚**：先自动创建 pre-rollback safety 提交（当前状态可找回），再恢复快照内容并删除快照之后新增的文件（`git checkout` 本身不删新增路径，不补删会让后续章节残留），最后把回滚结果落为显式 `[auto] rollback to …` 提交——回滚成为版本链上的可见节点，不会被审阅面板的 checkpoint 裹进待审阅批次或被「丢弃」静默吞掉。快照列表支持 `?limit=` 查询（默认 20，前端传 200 使早期里程碑可达）。

**审阅门（双分支）**：顶部「审阅」面板列出 draft 相对 main 的待审阅改动，支持三种操作——**逐文件接受/拒绝**（`POST /review/files/accept|reject`，body `{ path }`，只处理单个文件，其余保持待审阅）、整批合并（ff main 到 draft；历史分叉时返回 409 与可操作错误，不再静默普通合并破坏 main 镜像）、整批丢弃（reset draft 到 main，含后悔药安全提交）。

**git 同步**：`POST /:id/sync` 同步推 draft + main 双分支（远程 main 不再长期滞后）；main 推送失败不影响整体成功并在消息中如实报告。

**导出**：markdown/text 导出会把质检归档章节与缺失章节记入响应头 `x-export-warnings`，前端读取后 toast 提示（缺章不再静默）。章节文件识别放宽：「第3章 风雪夜.md」/全角数字等近似命名同样参与 resync/门禁/导出。EPUB/DOCX 复用同一套章节排序与缺章/归档判定：EPUB 3 的 `mimetype` 为 ZIP 首条且不压缩，`content.opf` 的 spine 按章号排列，每章一个 XML 转义后的 XHTML；DOCX 含标题页、章节标题（Heading 1）与中文首行缩进，正文中的 `& < > " '` 均安全转义。质检归档章节不会出现在两种电子书导出中。

### 3.5 项目管理补充

```bash
# 删除项目：默认仅移出列表（文件保留在磁盘），removeFiles=true 时连同目录删除（不可恢复）
# removeFiles=true 时校验目录内容白名单：目录含 .novel/.git/.gitignore 之外的条目
# （如个人文件）时拒绝删除（409 dir-not-exclusive），防止连坐误删。
DELETE /api/projects/{id}?removeFiles=true

# 创建项目：目录已存在 .novel/ 结构时返回 409 workspace-exists（请走「打开项目」）；
# 目录已存在且非空时返回 warning 字段（前端 toast 提示：现有文件会卷入版本库）。
POST /api/projects

# 打开项目：按磁盘产出反推 currentStage（≥3 章→writing，1-2 章→sample，
# 有 scenes.md→sample，有大纲→scenes，有角色档案→outline，…），
# 存量项目导入后不再停留在「概念」阶段。
POST /api/projects/import
```

**项目串行锁**：同项目同时刻只允许一个 run。所有写路径——回滚、版本快照、改名、导入源文本、git 同步、删除项目/章节、文件上传/写入、模板生成、审阅合并/丢弃、章节正文保存——在 run 运行期间一律返回 409 `run-in-progress`（`POST /api/runs` 与 `POST /rewrite` 同理），防止与 agent 写盘互踩。

### 3.5.1 导入手稿（txt / md / epub）

首页「导入手稿」打开三步向导：上传 → 预览并调整边界 → 确认导入（可导入已有项目或新建项目）。

```bash
# 预览：只解析与切章，不写任何文件（multipart 字段 file，或 JSON text / contentBase64）
POST /api/projects/import-manuscript/preview
{ "filename": "book.txt", "text": "第一章 ..." }

# 提交：chapters 来自预览结果中用户调整后的 { title, content }
POST /api/projects/{id}/import-manuscript/commit
{
  "chapters": [{ "title": "少年", "content": "正文..." }],
  "finalized": true,      # 默认 true：标记章节状态为 finalized（不足 100 字自动降为 draft）
  "overwrite": false,     # 已有同名章号时默认 409 chapters-exist，确认后传 true（原文件备份为 .bak）
  "backfill": true,       # 可选：导入后启动 enrich run 补全章节摘要与角色状态（只增不覆盖）
  "agentId": "pi"
}
```

- 切章规则：优先「第N章/回/节/篇/卷」（含中文数字「一百零五」与全角数字）、`Chapter N`；无强标记时依次尝试 Markdown `#`/`##`、`1.`/`1、` 数字标题；都没有则按段落固定大小切分并返回 warning。标题前的前言并入第 1 章，空正文章节跳过。
- 编码：UTF-8（含 BOM）优先；非法 UTF-8 时回退 GB18030（兼容 GBK）。EPUB 按 `META-INF/container.xml → OPF spine` 顺序提取纯文本（h1/h2 会保留为 Markdown 标题参与切章），`nav` 目录页不进入正文。
- 写入：章节文件固定为 `.novel/chapters/第N章.md`（N 为连续章号），**标题只写入正文首行，绝不参与路径拼接**；同步更新 `.novel/chapter-status.json`、`config.json`、`chapters` 表缓存，并在 git 互斥内创建 draft 快照。定稿导入后按定稿章数自动推进项目阶段（≥3 章 → writing，1–2 章 → sample，只前进不回退）。存在活跃 run 时返回 409 `run-in-progress`。
- 自动补全复用现有 `enrich` 阶段（不重复实现摘要逻辑），以真实 run 注册（可在会话列表查看/取消）。

**数据库备份与恢复**：

```bash
POST /api/backup             # 立即备份（无变更时跳过并返回已有备份）
GET  /api/backup             # 列出备份（最新在前）
POST /api/backup/restore     # 从指定备份恢复（body: { "filename": "..." }，须为列表中的文件名）
```

恢复会关闭并重建当前 PGlite 实例，原数据目录保留为 `pglite.corrupted.*` 供排查；建议在所有写作任务结束后调用。存在活跃 run 时 restore 端点直接返回 409（全局排他锁），防止 run 收尾写库撞上已关闭的 DB。

### 3.6 语义检索（可选，默认关闭）

在「设置 → 语义检索」配置 OpenAI 兼容嵌入服务（Base URL / 模型 / API Key）。API Key 仅存服务端，`GET /api/settings` 不回显，只返回 `embedding_apiKeySet`；PATCH 传空字符串可清除密钥。启用后章节正文与摘要会发送到该服务建立索引（默认关闭，未配置时搜索与提示词组装行为与旧版完全一致）。

```bash
# 搜索：mode 默认 text（旧行为）；semantic/hybrid 需要已配置并完成索引
# 未配置 / 嵌入调用失败 / 索引为空时自动回退文本搜索，并在 fallback 字段说明原因：
# not-configured | embedding-error | index-empty
GET /api/projects/{projectId}/search?q=龙&mode=semantic|text|hybrid

# 手动增量重建索引（同项目有活跃 run 时 409；未配置时 400；?force=true 忽略哈希强制重嵌）
POST /api/projects/{projectId}/search/reindex
```

索引在章节同步、正文保存、章节删除后自动后台触发（4s 防抖；有活跃 run 时跳过，run 结束后的下一次同步补齐）。每块保存 sha256 哈希：未变化章节整章跳过，变化章节只嵌入新增/变化块（相同文本跨章复用向量）；更换嵌入模型后整项目向量自动重建——在「设置 → 语义检索」保存新模型/地址/密钥时会立即触发全量重建（后台进行），换模型当场生效，不必等下一次章节同步。正文与摘要都入索引。

当前安装的 PGlite 0.5.8 未内置 pgvector，向量以 `real[]` 存储并在 JS 侧计算余弦相似度（外部 postgres 同样适用，无需 CREATE EXTENSION）。写作阶段会以「本章大纲 + 上一章摘要/正文尾部」为查询，检索最多 3 个更早章节的高相关片段（总计 ≤1500 字）注入提示词；未配置或检索失败时不注入任何内容。

## 4. 写作管道详解

### 4.1 一次写作 run 的完整生命周期

```
用户 POST /api/runs
    │
    ├─ 1. 创建 conversation + 存储用户消息
    ├─ 2. composePrompt() 组装分层上下文
    │      ├─ 核心设定层：concept.md + world-building.md（全文）
    │      ├─ 状态层：state.json（角色位置/情绪/已知信息/关系）
    │      ├─ 本章大纲块：outline-detailed.md 第N章片段
    │      ├─ 本章出场角色层：profiles/{角色}.md 分级注入 + 声口库（可选）
    │      ├─ 滚动摘要层：最近章节的 .summary.md
    │      └─ 伏笔层：foreshadow.json 中 status=pending 的伏笔
    │      ├─ 3. startPiAgent() 创建进程内 Pi session
    │      │      ├─ createAgentSession({ cwd, tools, modelRuntime })
    │      │      ├─ ModelRuntime：内置 provider / 自定义反代
    │      │      └─ agent 读大纲/场景/前文 → 写章节 → 写摘要 → 更新 state
    │      ├─ 4. session.subscribe 事件映射（text/thinking/tool_use/tool_result/usage）
    ├─ 5. Pi run 结算收尾：
    │      ├─ collectWrittenPaths：从事件提取写入的文件路径
    │      ├─ transformStreamEvents：合并 text/thinking delta → 持久化格式
    │      ├─ 存储assistant消息到 messages 表（events + artifacts 列）
    │      ├─ syncFilesToDb：文件变更同步到 DB
    │      ├─ ensureContextArtifacts：兜底补摘要 + 修复 state.json
    │      └─ createSnapshot：git commit 快照
    └─ 6. 返回 { runId, conversationId }
```

### 4.2 上下文分层（关键设计）

写作阶段的 prompt 由 `composePrompt()` 组装，分六层注入：

| 层 | 来源 | 作用 | 注入条件 |
|---|---|---|---|
| 核心设定 | concept.md + world-building.md | 恒定世界观锚点 | 写作阶段（writing/drafting/revision/polish） |
| 状态 | state.json | 角色当前位置/情绪/已知/关系 | 文件存在时 |
| **本章大纲** | **outline-detailed.md 第N章块** | **本章发生什么** | **写作阶段（大纲块提取）** |
| **本章出场角色** | **profiles/{角色}.md 分级注入** | **角色是谁、出身、驱动力、声口** | **写作阶段（三级回退识别）** |
| POV 知情边界 | character-knowledge.json + state.json knows | 视点角色此刻已知/尚不知，防止越界知情 | 识别到 POV 且存在知情数据（无数据不注入） |
| 滚动摘要 | 第N-K章的 `.summary.md` | 前文回顾（避免全量塞入） | buildRollingSummaryContext() |
| 语义回忆（可选） | semantic_chunks（更早章节 top-k 片段） | 补足摘要压缩丢失的设定/伏笔细节 | 已配置嵌入服务且检索命中（≤3 章 / ≤1500 字） |
| 活跃伏笔 | foreshadow.json | 待兑现伏笔（标注类型/权重/期限/依赖/推进记录 + 密度预算 + 逾期/临期提醒） | status=pending/planted/progressing 的条目 |
| 精排窗口 | 从 lastUpdatedChapter 推算 | 提醒即将写作的章节应先精化为 beat 级 | 写作阶段注入 |

**出场角色分级注入**：POV 角色与显式出场角色按 L1 完整注入（出身/驱动力/性格等关键段，≤6KB/人）；仅被提及的角色按 L2 速查卡注入（~150 字）。角色层总预算 20KB，超出降级为 L2。声口库（`characters/voices/{角色}.md`）为可选资产，存在时附入 L1 角色。

**非写作阶段**（concept/world/characters/outline/scenes）不注入后三层，因为这些阶段还没有章节内容。

### 4.3 state.json 结构

```json
{
  "characters": [
    {
      "name": "林冲",
      "location": "翠微谷禁地",
      "emotion": "决心已定",
      "knows": ["令牌真相", "父亲守秘术"],
      "relationships": { "孙二娘": "脆弱的盟友" },
      "lastAppearance": 17
    }
  ],
  "timeline": "全书完",
  "activeForeshadows": [1, 3, 4],
  "foreshadowProgress": { "1": "承接（第15章...）" },
  "lastUpdatedChapter": 17,
  "updatedAt": "2026-07-03T17:30:00Z"
}
```

### 4.4 ensureContextArtifacts 兜底机制

agent 不总是可靠地写摘要和更新 state。`ensureContextArtifacts()` 在 run 结束时兜底：

1. **摘要兜底**：检测新写入的章节缺少 `.summary.md` 时，生成占位摘要
2. **state.json 修复**：`repairOrInitState()` 处理 LLM 常见 JSON 格式错误：
   - 键名含冒号：`"林冲:text"` → `"林冲": "text"`
   - 时间戳被拆：`"2026-07-03T18": "00:00Z"` → `"2026-07-03T18:00:00Z"`
3. **章节号更新**：从写入路径推断 lastUpdatedChapter

### 4.5 编辑器模式与成本提醒

写作视图的章节编辑器有三种模式：

| 模式 | 说明 |
|---|---|
| 编辑 | Markdown 源码 textarea；内联 AI（润色/扩写/续写，选区感知、diff 预览后应用）在此模式使用 |
| 富文本 | WYSIWYG：标题、加粗、斜体、引用、无序/有序列表可视化编辑；保存/自动保存仍是 Markdown，不引入 Markdown 之外的数据格式 |
| 预览 | `react-markdown` 渲染 + 实体名可点击 |

富文本使用 `marked` 渲染 + `turndown` 回写 Markdown，渲染前做标签/属性白名单清洗（丢弃 raw HTML、`javascript:` 链接与事件处理器），粘贴一律按纯文本处理。外部改动（切换章节、源码模式应用内联 AI）会同步回富文本编辑器。

**run 级实时成本提醒**：在「成本」面板设置预算（`cost_budget_usd`，USD）后，服务端在 run 启动时快照项目累计花费，并在每条 `runtime_usage` 上累加本次 run 成本；首次越过预算时通过 SSE 推送一次 `cost_alert`，对话输入区上方出现可关闭的提醒条。提醒只出现一次/run，预算未设置或为 0 时不提醒；成本聚合与预算口径与 `GET /api/projects/:id/costs/summary|budget` 完全同源。局部重写（`POST /api/projects/:id/rewrite`）的 run 不绑定对话、不计入项目累计，因此不触发该提醒。

## 5. 批量写作

### 单章触发（推荐）

逐章触发，本章大纲与出场角色档案已自动注入：

```bash
curl -X POST http://localhost:3006/api/runs \
  -H "Content-Type: application/json" \
  -d '{
    "projectId": "proj_xxx",
    "agentId": "pi",
    "stage": "writing",
    "skillId": "wuxia",
    "message": "请写第N章正文。"
  }'
```

### 批量触发（前端 / API）

在会话框输入 `/batch 10-20` 或「写第10到20章」即可启动批量写作（单批最多 10 章）。批量不是隐藏后台任务：每章仍是一次真实的 `POST /api/runs`（走项目串行锁、样章门、runs 表注册），前端逐章推进。

- **暂停**：当前章继续写完，结束后停在下一章；**继续**从该章接着写；**取消**立即终止。
- **失败不跳章**：某章失败后批量停止，记录 `resumeChapter`；点「继续」从失败章重试。
- **刷新/重启可恢复**：状态落盘 `.novel/batch.json`，页面重载后显示批量横幅，由用户点「继续」恢复（不会未经确认自动续跑）。
- **API**：`GET/POST /api/projects/:id/batch`、`POST .../batch/{pause,resume,cancel,advance,run-started}`。项目有活跃 run 时 `POST` 创建/恢复返回 409 `run-in-progress`。

### 自动里程碑与回顾

- **每 K 章**：`.novel/config.json` 的 `milestoneEvery`（默认 50，`0` 关闭按章里程碑；也可 `PATCH /api/projects/:id { milestoneEvery: 50 }`）。达到边界后创建带标签快照 `milestone-chapter-N`。
- **卷末**：`.novel/volumes.json`（`{ "volumes": [{ "name": "...", "startChapter": 1, "endChapter": 60 }] }`）或 `outline-meta.json` 的 `volumes` 字段；写完卷末章创建 `milestone-volume-N`。
- **幂等**：边界记录落盘 `.novel/milestones.json`，服务重启后不会对同一边界重复创建；快照创建遵守 git 结构互斥与 main/draft 双分支不变量。
- **回顾 run**：里程碑创建后，若无活跃 run（且批量未在进行），以正常 run（`stage=retro`）生成 `.novel/retro/里程碑-<label>.md`；有 run 在途则跳过并在账本记录 note，后续评估重试，不排队隐藏任务。

### 轮询等待完成

```bash
# 等待章节文件出现（agent 超时 30 分钟，建议轮询间隔 10 秒）
CHAPTER_FILE=".novel/chapters/第N章.md"
while [ ! -f "$CHAPTER_FILE" ]; do sleep 10; done
```

### 注意事项

- **服务端强制串行**：同一项目同时刻只允许一个 run——并行写多章会互相污染 state.json（`POST /api/runs` 返回 409 `run-in-progress`）。前端 run 进行中会禁用发送按钮
- **「下一章」推断**：写作上下文优先取用户消息中显式指定的章号（如「写第3章」），否则扫描 `chapters/` 目录取最小未写章（从 1 起第一个缺文件的章）——样章写了第 1、5、12 章后，正式写作自动从第 2 章续写
- **监控退化**：长上下文运行可能导致 token 退化（重复词暴增）
- **定期检查 state.json**：确认 `lastUpdatedChapter` 跟上实际进度

## 7. 已知限制

| 问题 | 影响 | 临时方案 |
|---|---|---|
| state.json 更新不可靠 | 后续章节可能读到过时状态 | 手动检查并修正 state.json |
| 长运行 token 退化 | 中段章节可能出现高频重复词 | 单章触发，避免连续大量写作 |
| 字数控制不精确 | 章节长度差异可达 2-4 倍 | 在 message 中明确字数约束 |
| wyw + babel TS 冲突 | 首页可能渲染报错 | 待修复（linaria 插件 TS 解析问题） |
