# open-novel 工具使用指南

> open-novel 是 AI 驱动的长篇小说创作系统。
> 技术栈：React 19 + Hono + PGlite + Drizzle + Linaria + Vite + AI Agent（Claude Code / OpenCode / Oh My Pi）

---

## 1. 快速开始

### 1.1 启动开发服务器

```bash
pnpm install
pnpm dev          # 启动 vite dev server（含 API），默认端口 3006
```

生产构建：

```bash
pnpm build        # build:client + build:server
pnpm start        # node dist/server/api.js
```

### 1.2 前置条件

- 至少一种 AI Agent CLI 已安装并在 PATH 中：
  - **Claude Code**：`claude --version`
  - **OpenCode**：`opencode --version`
  - **Oh My Pi (omp)**：`omp --version`（需支持 `omp acp` 子命令）
- agent 超时配置：环境变量 `AGENT_TIMEOUT_MS`（默认 1800000 = 30 分钟）

---

### 2.1 创作流程（七阶段）

open-novel 的创作分七个阶段，每个阶段由 agent 通过 API 触发，产出写入 `.novel/` 目录：

```
concept → world → characters → outline → scenes → sample → writing
 构思     世界观    角色档案     大纲      场景表    样章门    正文写作
```

**样章门（sample）**：scenes 与 writing 之间的强制关卡——写 3 章样章（第 1 章 + 自选 2 个关键章节）检验声口与节奏，每章在 `.novel/sample-feedback.md` 追加复盘（声口落地/节奏体感/世界观落地/大纲需修正点），3 章完成后按复盘修订大纲再进入正式写作。后端门禁：`POST /api/runs` 的 `stage` 为 **writing / drafting / revision / polish** 时扫描磁盘 `.novel/chapters/` 与 `.novel/degraded/` 目录，有效正文（CJK 字数 ≥100）不足 3 章返回 409 `sample-gate`（质检归档章节同样计入，归档可一键恢复，不重新卡门；409 响应带 degradedChapters 章号列表），携带 `force: true` 可旁路；存量项目（≥3 章）不受影响。revision/polish 同样拦截——否则「`/revision` 写第2章」即可绕过样章门。**复盘门**：以 config.json `sampleStageCompleted` 标记为判据（sample run 成功后磁盘正文 ≥3 章时自动写入）——经历过样章阶段就要求 sample-feedback.md 中 ≥3 篇结构化复盘（`- **声口落地**：` 节标题计数，旧格式回退子串计数），文件缺失/不足同样返回 409 `sample-gate`（feedbackCount 字段给出实际篇数）；存量项目无标记时回退旧判据（复盘文件存在则要求 ≥3 篇）；`import-source` 逆向拆书项目（config.json `sourceImported: true`）豁免复盘要求。force 旁路会落盘记录（config.json `sampleGateBypassed: true`），总览页黄色警示徽标；门槛后续达标时自动清除（惩罚可逆）。前端收到 409 后显示双按钮：「去写样章」/「仍要开始正式写作」（二次确认后 force 旁路）。

**阶段切换**：顶部进度条点击、或对话面板工具栏的阶段下拉，都会 `PATCH /api/projects/{id}` 落库 `currentStage`（写作子模式 drafting/revision/polish 仅切视图不落库）。切换后立即发送的消息即按新阶段组装提示词，无需等 agent 回写阶段。`POST /api/runs` 的 `stage` 有枚举校验：未知值返回 400 `invalid-stage`（合法值 = 七阶段 + drafting/revision/polish/decompose/enrich）。

**提问挂起上限**：规划阶段的采访式提问（ask）挂起期间 run 超时计时暂停（用户思考不计时），但提问本身有最长挂起时限 `ASK_TIMEOUT_MS`（默认 24 小时）——到期自动结束整个 run（agent 不再带着缺省答案继续写盘），防止用户关闭浏览器后 run 与项目写锁被永久占用；到期前 1 小时经 SSE 推送提醒。提问挂起期间项目其他写操作锁定，前端有提示。提问过期后用户提交的答案会暂存（响应带 `late: true`），经重试端点回传并补入重试请求，不静默丢弃。

**deepen 收敛准则**：深化审查报告的每条发现必须标注 `[P0]`（结构性缺陷）/`[P1]`（重要问题）/`[P2]`（打磨建议）。当某轮审查无 P0/P1 时视为收敛：修订轮改为冻结轮——P2 建议逐条记入 `.novel/deepen-backlog.md`，禁止再修改产出文件。防止"审查永远找得出问题"的规划螺旋。

**滚动式大纲**：大纲章节卡片带三级承诺等级（引用行元数据 `> commitment: committed|tentative|open`，`open` 须附 `> open-questions:` 待决策列表）。粒度梯度近细远粗：第 1-10 章 committed/beat 级，第一幕其余 tentative/arc 级，二三幕 open/骨架级——远期粗粒度是设计而非未完成。写作 prompt 会按当前进度注入"精排窗口"提醒（已写章节向后 10 章应精化为 beat 级）。`outline/index.md` 在每次合并读取时自动重建自愈（章号取自卡片文件名）。

### 阶段产出文件

| 阶段 | 产出文件 | 内容 |
|---|---|---|
| concept | `.novel/concept.md` | 核心概念、前提、主要冲突 |
| world | `.novel/world-building.md` | 世界设定、规则、历史、文化 |
| characters | `.novel/characters/profiles.md` | 角色动机、背景、关系、弧光 |
| outline | `.novel/outline-detailed.md` | 逐章大纲（幕、节拍、字数分配） |
| scenes | `.novel/scenes.md` | 逐章场景（主动 Scene / 被动 Sequel） |
| sample | `.novel/chapters/第N章.md` + `.novel/sample-feedback.md` | 3 章样章 + 复盘（声口/节奏/世界观/大纲修正） |
| writing | `.novel/chapters/第N章.md` | 正文 + `.summary.md` + `state.json` |

### 阶段推进

每阶段完成后，agent 通过 PATCH 推进阶段：

```bash
curl -X PATCH http://localhost:3006/api/projects/{projectId} \
  -H "Content-Type: application/json" \
  -d '{"currentStage": "world"}'
```

## 3. 核心 API

### 3.1 项目管理

```bash
# 创建项目
POST /api/projects
{
  "title": "令牌",
  "genre": "wuxia",
  "chapterCount": 20,
  "targetWords": 80000
}

# 获取项目信息
GET /api/projects/{id}

# 更新阶段
PATCH /api/projects/{id}
{ "currentStage": "writing" }

# 生成逐章模板脚手架（大纲/场景）
POST /api/projects/{id}/generate-templates

# 预览模板（不落盘）
GET /api/projects/{id}/templates/outline-detailed
GET /api/projects/{id}/templates/scenes
```

### 3.2 触发 Agent 写作（核心）

```bash
POST /api/runs
{
  "projectId": "proj_xxx",
  "agentId": "claude",        # claude | opencode | omp（前端自动选首个可用者）
  "stage": "writing",          # concept|world|characters|outline|scenes|writing
  "skillId": "wuxia",          # 插件技能 ID（决定写作风格指导）
  "message": "你的指令..."     # 具体任务描述
}
```

**响应**：
```json
{ "runId": "d2e0ed05-...", "conversationId": "conv_xxx" }
```

**事件流**：通过 SSE 实时获取 agent 事件：
```
GET /api/runs/{runId}/events      # SSE 流
```

### 3.3 质量检查

```bash
# AI 味检测（检测碎片化句型、重复词等）
POST /api/projects/{projectId}/check/ai-patterns
{ "chapterNum": 18 }

# 一致性检查（角色状态、时间线连贯性）
POST /api/projects/{projectId}/check/consistency

# 节奏检查
POST /api/projects/{projectId}/check/pacing
```

### 3.3 伏笔债务系统

伏笔是结构化数据（`.novel/foreshadow.json`），字段：`type`（chekhov/identity/emotional/world）、`status`（pending/planted/resolved/dropped）、`plantedIn`/`resolveDeadline`/`resolvedIn`（严格章号）、`dependsOn`（前置伏笔 id 列表）、`weight`（major/light）。旧格式（plantedIn 为自由文本）读取时自动迁移。

```bash
# 清单 + 债务统计（debtScore/overdue/dueSoon/orphaned/密度）
GET /api/projects/{projectId}/foreshadows

# CRUD
POST   /api/projects/{projectId}/foreshadows          # 创建
PATCH  /api/projects/{projectId}/foreshadows/{fid}    # 更新
DELETE /api/projects/{projectId}/foreshadows/{fid}    # 删除（自动清理依赖引用）
```

写作 prompt 注入密度预算（默认"每 3 章新埋 ≤2 条"）与本章到期提醒；前端伏笔视图为四列看板（待埋/已埋/已收/放弃）+ 债务摘要条 + 甘特图（◆=期限）。

### 3.4 回溯影响分析（设定修订）

```bash
# 修改设定文件后，扫描受影响面（正文提及/大纲提及/伏笔提及），报告落盘 .novel/retro/
POST /api/projects/{projectId}/retro
{ "file": "world/index.md", "note": "修订说明" }

# 状态卫生：检测规划期数据对运行态 state.json 的污染（只读）
GET /api/projects/{projectId}/state-hygiene
```

状态分离约定：`.novel/state.json` 只存运行态（由正文产生）；规划期期望写入 `.novel/state-intent.json`。每次写作 run 结束时自动执行污染分离自愈（`splitPlanningPollution`）。

### 3.4 章节管理

```bash
# 列出所有章节（GET 时自动按磁盘全量 resync：补缺失、刷新字数、删除磁盘已不存在的行）
GET /api/projects/{projectId}/chapters

# 创建章节：DB 行 + 磁盘空正文文件（含标题行）同步创建，文件已存在时不覆盖
POST /api/projects/{projectId}/chapters

# 手动重新同步磁盘章节到 DB（全量对齐：磁盘是事实源，DB 仅缓存元数据）
POST /api/projects/{projectId}/chapters/resync

# 删除章节（同步删除正文与摘要文件，避免 resync 加回；自动清理伏笔 plantedIn/resolvedIn 悬挂引用；
# 支持 ?renumber=true 或 body { renumber: true }：后续章节章号前移一位——正文/摘要/大纲卡片/DB 行/伏笔引用（含 resolveDeadline）同步平移，避免章号空洞导致「写下一章」永远回到被删章号）
DELETE /api/projects/{projectId}/chapters/{num}?renumber=true

# 列出质检归档章节（.novel/degraded/ 隔离目录 + 旧版 chapters/*.degraded.md）
GET /api/projects/{projectId}/chapters/degraded

# 恢复归档章节到正文（目标章节已存在正文时返回 409，避免覆盖重写内容）
POST /api/projects/{projectId}/chapters/degraded/{num}/restore

# 导出（markdown 支持 ?scope=manuscript 仅正文，默认 full 含概念/世界观/角色设定）
POST /api/projects/{projectId}/export
```

写后质检（退化终检/AI 味检测）不通过时：仅成功且写作产出阶段（writing/sample/drafting）的章节会被移入 `.novel/degraded/` 隔离目录——不再就地改名隐藏；写作视图显示「已归档」分组，可一键恢复。失败 run 与 revision/polish/decompose 只告警不归档，避免误伤导入原文与修订稿。

回滚快照（`POST /api/runs/projects/{id}/rollback`）后服务端会自动 resync 章节表，避免写作视图出现幽灵章节。回滚是**完整回滚**：先自动创建 pre-rollback safety 提交（当前状态可找回），再恢复快照内容并删除快照之后新增的文件（`git checkout` 本身不删新增路径，不补删会让后续章节残留），最后把回滚结果落为显式 `[auto] rollback to …` 提交——回滚成为版本链上的可见节点，不会被审阅面板的 checkpoint 裹进待审阅批次或被「丢弃」静默吞掉。快照列表支持 `?limit=` 查询（默认 20，前端传 200 使早期里程碑可达）。

**审阅门（双分支）**：顶部「审阅」面板列出 draft 相对 main 的待审阅改动，支持三种操作——**逐文件接受/拒绝**（`POST /review/files/accept|reject`，body `{ path }`，只处理单个文件，其余保持待审阅）、整批合并（ff main 到 draft；历史分叉时返回 409 与可操作错误，不再静默普通合并破坏 main 镜像）、整批丢弃（reset draft 到 main，含后悔药安全提交）。

**git 同步**：`POST /:id/sync` 同步推 draft + main 双分支（远程 main 不再长期滞后）；main 推送失败不影响整体成功并在消息中如实报告。

**导出**：markdown/text 导出会把质检归档章节与缺失章节记入响应头 `x-export-warnings`，前端读取后 toast 提示（缺章不再静默）。章节文件识别放宽：「第3章 风雪夜.md」/全角数字等近似命名同样参与 resync/门禁/导出。

### 3.5 项目管理补充

```bash
# 删除项目：默认仅移出列表（文件保留在磁盘），removeFiles=true 时连同目录删除（不可恢复）
# removeFiles=true 时校验目录内容白名单：目录含 .novel/.git/.gitignore 之外的条目
# （如个人文件）时拒绝删除（409 dir-not-exclusive），防止连坐误删。
DELETE /api/projects/{id}?removeFiles=true

# 创建项目：目录已存在 .novel/ 结构时返回 409 workspace-exists（请走「打开项目」）；
# 目录已存在且非空时返回 warning 字段（前端 toast 提示：现有文件会卷入版本库）。
POST /api/projects

# 打开项目：按磁盘产出反推 currentStage（≥3 章→writing，1-2 章→sample，
# 有 scenes.md→sample，有大纲→scenes，有角色档案→outline，…），
# 存量项目导入后不再停留在「概念」阶段。
POST /api/projects/import
```

**项目串行锁**：同项目同时刻只允许一个 run。所有写路径——回滚、版本快照、改名、导入源文本、git 同步、删除项目/章节、文件上传/写入、模板生成、审阅合并/丢弃、章节正文保存——在 run 运行期间一律返回 409 `run-in-progress`（`POST /api/runs` 与 `POST /rewrite` 同理），防止与 agent 写盘互踩。

**数据库备份与恢复**：

```bash
POST /api/backup             # 立即备份（无变更时跳过并返回已有备份）
GET  /api/backup             # 列出备份（最新在前）
POST /api/backup/restore     # 从指定备份恢复（body: { "filename": "..." }，须为列表中的文件名）
```

恢复会关闭并重建当前 PGlite 实例，原数据目录保留为 `pglite.corrupted.*` 供排查；建议在所有写作任务结束后调用。存在活跃 run 时 restore 端点直接返回 409（全局排他锁），防止 run 收尾写库撞上已关闭的 DB。

## 4. 写作管道详解

### 4.1 一次写作 run 的完整生命周期

```
用户 POST /api/runs
    │
    ├─ 1. 创建 conversation + 存储用户消息
    ├─ 2. composePrompt() 组装分层上下文
    │      ├─ 核心设定层：concept.md + world-building.md（全文）
    │      ├─ 状态层：state.json（角色位置/情绪/已知信息/关系）
    │      ├─ 本章大纲块：outline-detailed.md 第N章片段
    │      ├─ 本章出场角色层：profiles/{角色}.md 分级注入 + 声口库（可选）
    │      ├─ 滚动摘要层：最近章节的 .summary.md
    │      └─ 伏笔层：foreshadow.json 中 status=pending 的伏笔
    │      ├─ 3. launchAgent() 启动 agent 子进程
    │      │      ├─ Claude Code：stream-json 模式（stdin 写 prompt）
    │      │      ├─ OpenCode：--prompt 单发模式（stdout 读流）
    │      │      └─ omp：ACP 协议模式（stdin/stdout 双向 JSON-RPC，经 acp-bridge 驱动）
    │      │      └─ agent 读大纲/场景/前文 → 写章节 → 写摘要 → 更新 state
    │      ├─ 4. stream-parser / acp-bridge 解析 agent 输出流（text/tool_use/tool_result）
    ├─ 5. child.on('close') 收尾：
    │      ├─ collectWrittenPaths：从事件提取写入的文件路径
    │      ├─ transformStreamEvents：合并 text/thinking delta → 持久化格式
    │      ├─ 存储assistant消息到 messages 表（events + artifacts 列）
    │      ├─ syncFilesToDb：文件变更同步到 DB
    │      ├─ ensureContextArtifacts：兜底补摘要 + 修复 state.json
    │      └─ createSnapshot：git commit 快照
    └─ 6. 返回 { runId, conversationId }
```

### 4.2 上下文分层（关键设计）

写作阶段的 prompt 由 `composePrompt()` 组装，分六层注入：

| 层 | 来源 | 作用 | 注入条件 |
|---|---|---|---|
| 核心设定 | concept.md + world-building.md | 恒定世界观锚点 | 写作阶段（writing/drafting/revision/polish） |
| 状态 | state.json | 角色当前位置/情绪/已知/关系 | 文件存在时 |
| **本章大纲** | **outline-detailed.md 第N章块** | **本章发生什么** | **写作阶段（大纲块提取）** |
| **本章出场角色** | **profiles/{角色}.md 分级注入** | **角色是谁、出身、驱动力、声口** | **写作阶段（三级回退识别）** |
| 滚动摘要 | 第N-K章的 `.summary.md` | 前文回顾（避免全量塞入） | buildRollingSummaryContext() |
| 活跃伏笔 | foreshadow.json | 待兑现伏笔（标注类型/权重/期限/依赖 + 密度预算） | status=pending/planted 的条目 |
| 精排窗口 | 从 lastUpdatedChapter 推算 | 提醒即将写作的章节应先精化为 beat 级 | 写作阶段注入 |

**出场角色分级注入**：POV 角色与显式出场角色按 L1 完整注入（出身/驱动力/性格等关键段，≤6KB/人）；仅被提及的角色按 L2 速查卡注入（~150 字）。角色层总预算 20KB，超出降级为 L2。声口库（`characters/voices/{角色}.md`）为可选资产，存在时附入 L1 角色。

**非写作阶段**（concept/world/characters/outline/scenes）不注入后三层，因为这些阶段还没有章节内容。

### 4.4 ensureContextArtifacts 兜底机制

agent 不总是可靠地写摘要和更新 state。`ensureContextArtifacts()` 在 run 结束时兜底：

1. **摘要兜底**：检测新写入的章节缺少 `.summary.md` 时，生成占位摘要
2. **state.json 修复**：`repairOrInitState()` 处理 LLM 常见 JSON 格式错误：
   - 键名含冒号：`"林冲:text"` → `"林冲": "text"`
   - 时间戳被拆：`"2026-07-03T18": "00:00Z"` → `"2026-07-03T18:00:00Z"`
3. **章节号更新**：从写入路径推断 lastUpdatedChapter

## 5. 批量写作

### 单章触发（推荐）

逐章触发，本章大纲与出场角色档案已自动注入：

```bash
curl -X POST http://localhost:3006/api/runs \
  -H "Content-Type: application/json" \
  -d '{
    "projectId": "proj_xxx",
    "agentId": "claude",
    "stage": "writing",
    "skillId": "wuxia",
    "message": "请写第N章正文。"
  }'
```

### 轮询等待完成

```bash
# 等待章节文件出现（agent 超时 30 分钟，建议轮询间隔 10 秒）
CHAPTER_FILE=".novel/chapters/第N章.md"
while [ ! -f "$CHAPTER_FILE" ]; do sleep 10; done
```

### 注意事项

- **服务端强制串行**：同一项目同时刻只允许一个 run——并行写多章会互相污染 state.json（`POST /api/runs` 返回 409 `run-in-progress`）。前端 run 进行中会禁用发送按钮
- **「下一章」推断**：写作上下文优先取用户消息中显式指定的章号（如「写第3章」），否则扫描 `chapters/` 目录取最小未写章（从 1 起第一个缺文件的章）——样章写了第 1、5、12 章后，正式写作自动从第 2 章续写
- **监控退化**：长上下文运行可能导致 token 退化（重复词暴增）
- **定期检查 state.json**：确认 `lastUpdatedChapter` 跟上实际进度

## 7. 已知限制

| 问题 | 影响 | 临时方案 |
|---|---|---|
| state.json 更新不可靠 | 后续章节可能读到过时状态 | 手动检查并修正 state.json |
| 长运行 token 退化 | 中段章节可能出现高频重复词 | 单章触发，避免连续大量写作 |
| 字数控制不精确 | 章节长度差异可达 2-4 倍 | 在 message 中明确字数约束 |
| wyw + babel TS 冲突 | 首页可能渲染报错 | 待修复（linaria 插件 TS 解析问题） |
